## Achados

### 1. ⭐⭐⭐ O sandbox rodava os arquivos de inicialização do shell fora de si mesmo

**Claude Code 2.1.309**, verbatim:

> *"Fixed sandboxed Bash commands on macOS and Linux running the shell's startup files outside the sandbox
> before each command"*

Para executar um comando **dentro** do sandbox, o harness invocava um shell, e os arquivos de
inicialização desse shell rodavam **fora** do sandbox, **antes de cada comando**. A contenção acontecia
depois daquilo que ela devia conter.

É o caso mais puro de duas formulações que eu já tinha, agora fundidas. Em 8/out eu escrevi, a partir do
`yarn --version` que executava configuração de projeto, que **detectar o ambiente é executar o ambiente**.
Em 11/out, a partir do `bubblewrap` gravável no `PATH`, que **construir o portão usa ferramentas que o
lado contido alcança**. Aqui não é detecção nem construção: é a **entrada** no sandbox que passa por um
programa cujo arquivo de configuração o lado contido escreve. E acontecia a cada comando, não uma vez por
sessão.

Na mesma versão, a mecânica de falha aberta ganha um gatilho novo, verbatim:

> *"Fixed hooks that run in PowerShell not blocking when the hook's program exits with code 2, and on
> Windows `PreToolUse` and `PermissionRequest` hooks with `"shell": "powershell"` failing open when Git
> for Windows isn't installed"*

Duas coisas. Gancho que sai com **código 2** não bloqueava — e código 2 é justamente a convenção de
bloqueio do mecanismo. E ganchos `PreToolUse` e `PermissionRequest` **falhando abertos quando o Git for
Windows não está instalado**.

A segunda é mecânica nova para a taxonomia do cap. 07, e eu a enuncio assim: **a dependência do portão
está ausente, logo o portão passa.** As oito que eu tinha eram sobre o conteúdo da política — arquivo
ilegível, lista vazia, preset permissivo, chave com erro de digitação, valor aninhado inválido, byte NUL,
falha de execução do gancho, entrada maior que o verificador. Esta é sobre o **ambiente** do portão: nada
na política está errado, e falta um programa de terceiro no disco.

Impacto **A** no cap. 07.

### 2. ⭐⭐⭐ Cinco portadores novos, quatro deles no verificador de Bash

A coluna de **portadores de leitura** que eu propus em 18/out ganha cinco linhas de uma vez. Verbatim:

> *"Fixed the Bash permission check trusting a variable set by a command whose redirect can fail to open"*
>
> *"Fixed Bash permission checks not prompting for some compound commands that change directory before
> running git when the `cd` is wrapped or prefixed, as they do for a plain `cd`"*
>
> *"Fixed an `Edit(path)` deny rule not blocking a Bash redirect to that path in some commands that also
> held a subshell"*
>
> *"Windows: Fixed PowerShell permission checks auto-approving some `Set-Location` or `cd` commands that
> target the current directory and carry extra arguments; these now prompt for approval"*

Variável definida por comando cujo redirecionamento pode falhar ao abrir; `cd` **embrulhado ou
prefixado**, que escapa do caso que o `cd` simples dispara; sub-shell mais redirecionamento derrotando uma
regra `Edit(path)`; e `Set-Location` com **argumentos a mais** apontando para o diretório atual.

Em 6/out eu concluí, de quatro advisories sobre `echo`, `rg`, `find` e `sed`, que **a lista que admite o
nome** pressupõe que o nome determina o efeito. Estas quatro linhas levam a conclusão um passo adiante: a
lista também pressupõe que **a forma sintática** é irrelevante, e ela não é. `cd` simples dispara, `cd`
prefixado não; `Set-Location` sozinho é checado, com argumento a mais não era. **O verificador falha uma
vez por forma, não só uma vez por nome.**

E o quinto portador é o velho, pela quarta e quinta vez. Verbatim:

> *"Fixed macOS sandbox `denyWrite` glob patterns not applying at a path's real location when the pattern's
> folder is reached through a symlink"*
>
> *"Fixed profile store write protection not applying when the config directory is reached through a
> symlink"*

Duas proteções diferentes, o mesmo symlink. Com os dois advisories de corpos distintos que eu comparei em
12/out — out/2025 e fev/2026 — e a escapada de sandbox de abr/2026, a família do symlink chega a **cinco
instâncias documentadas**, em quatro superfícies. É a reincidência mais bem estabelecida do acervo, e a
frase da primeira linha de hoje é a formulação canônica do eixo: a regra não se aplica **no lugar real do
caminho**.

Impacto **A** no cap. 07.

### 3. ⭐⭐ Revogação que não pega, herança que não desce, aprovação que a compactação come

Quatro linhas da 2.1.309 em três eixos abertos. Verbatim:

> *"Fixed a disabled MCP server being reconnected by a later permission prompt in print and SDK sessions"*

Servidor **desabilitado** reconectado por um **prompt de permissão** posterior. O desligamento não pegou, e
quem o desfez foi o fluxo de aprovação — isto é, o mecanismo de controle reativou o que o controle havia
desativado.

> *"Linux: Fixed sandbox write denies lifting when a background command outlived the session"*

Negações de escrita **se levantando** quando um comando de fundo sobrevive à sessão. Em 4/out o OpenClaw
me deu a melhor formulação do eixo — trabalho em curso termina quando se muda a configuração e para quando
o acesso é removido. Aqui o trabalho em curso sobrevive à sessão **e leva a negação consigo**, no sentido
errado.

> *"Fixed split-pane agent teammates not inheriting the tool deny and `--tools` rules given on the leader's
> command line"*

Colegas de equipe em painel dividido **não herdavam** as regras de negação do líder. É a falha de não
recursão que eu registrei em 7/out, quando a verificação de credencial do n8n não descia a subfluxos
aninhados — agora em segundo harness, e com a agravante de que a regra foi dada na linha de comando, que é
o lugar mais explícito que existe.

> *"Fixed Claude asking for permission on each artifact update for the rest of a turn after the
> conversation was compacted in that turn"*

E esta abre superfície nova: **a compactação come o estado de aprovação**. Depois de compactar no meio do
turno, a permissão passava a ser pedida a cada atualização. O eixo de cache e compactação, que eu
acompanho desde agosto com 24 ocorrências, encosta aqui no eixo de aprovação: o que a compactação descarta
inclui o que já havia sido autorizado.

Impacto **B** nos caps. 03, 04 e 07.

### 4. ⭐⭐ O harness como mensageiro de uma correção que ele não entrega

**OpenClaw 2026.10.6**. A versão abre declarando-se release de segurança, verbatim:

> *"**Security release:** v2026.10.6 adds remediations for the eMudhra certificate compromise. If you
> manage Node yourself, upgrade to Node 24.22.1 or newer (Node 24) or 26.12.1 or newer (Node 26) before
> starting OpenClaw."*

Leia a estrutura. O comprometimento é de **autoridade certificadora**, fora do harness. A correção de
verdade está no **Node**, fora do harness. E o que o harness faz é acrescentar remediações e **avisar o
operador que ele precisa atualizar outra coisa** — *"If you manage Node yourself"*, ou seja, só vale para
quem gerencia o próprio Node, e para esses o canal de entrega da correção não é o harness.

Isto fecha um trio sobre entrega que a semana montou sozinho. Em 20/out: o opencode **desligou a
atualização automática**, enquanto os advisories do Claude Code contam com ela para entregar correção. Em
22/out: **o canal de instalação decide a linha maior**. Hoje: **o harness pode ser o mensageiro de uma
correção que ele não entrega.** Para o cap. 12, a pergunta da ficha fica com três partes — quem instala,
por qual canal, e **o que o harness não pode consertar sozinho**.

⏳ **Não verifiquei o comprometimento em si.** O que eu afirmo é que o OpenClaw publica a versão como
remediação e exige as duas versões de Node que a nota nomeia; a existência e o escopo do incidente de
certificado são alegação da fonte, não achado meu.

Na mesma versão, uma linha que encosta no eixo de identidade, verbatim: *"Fixes old password settings
blocking Gateway credential setup. If you still use `CLAWDBOT_GATEWAY_PASSWORD`, switch to
`OPENCLAW_GATEWAY_PASSWORD` or a supported token."* A renomeação do produto — que o CVE de 3/out registrava
como *"OpenClaw (aka clawdbot or Moltbot)"* — deixou atrás de si uma **variável de credencial** com o nome
antigo, e ela chegou a bloquear a configuração da nova.

Impacto **B** nos caps. 12 e 07.
