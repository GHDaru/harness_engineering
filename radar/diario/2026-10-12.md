## Achados

### 1. ⭐⭐⭐ A mesma regra de negação furada por symlink, duas vezes, por dois pesquisadores

**GHSA-66m2-gx93-v996**, publicado em **3/out/2025**, CVE-2025-59829, **CWE-61**, CVSS v4 **2,3**,
corrigido na **v1.0.120**, relatado por `vinai`. Corpo verbatim:

> *"Claude Code failed to account for symlinks when checking permission deny rules. If a user explicitly
> denied Claude Code access to a file and Claude Code had access to a symlink pointing to that file, it
> was possible for Claude Code to access the file."*

**GHSA-4q92-rfm6-2cqx**, publicado em **6/fev/2026**, CVE-2026-25724, **CWE-61 e CWE-285**, CVSS v4
**2,3**, corrigido na **v2.1.7**, relatado por `ofirh`. Corpo verbatim:

> *"Claude Code failed to strictly enforce deny rules configured in settings.json when accessing files
> through symbolic links. If a user explicitly denied Claude Code access to a file (such as /etc/passwd)
> and Claude Code had access to a symbolic link pointing to that file, it was possible for Claude Code to
> read the restricted file through the symlink without triggering deny rule enforcement."*

Textos distintos, dois CVE, dois relatores independentes, e versões corrigidas em **ramos maiores
diferentes** — `v1.0.120` e `v2.1.7`. Nada aqui se parece com o caso Yarn de 9/out, em que o mesmo corpo
ocupava dois registros.

**A afirmação que eu posso sustentar, com o cuidado devido:** o mesmo *defeito descrito* foi corrigido
duas vezes, com quatro meses de intervalo, em duas versões maiores, por achado de dois pesquisadores que
não se conhecem. Não afirmo regressão do mesmo trecho de código, porque nenhum dos dois corpos fala de
código. O que afirmo é que **a propriedade que o harness prometeu em outubro deixou de valer em
fevereiro**, e que a segunda descoberta não dependeu da primeira.

Isto reabilita, com fonte melhor, a frase que eu escrevi em 6/out e relativizei em 9/out: há reincidência
de família, e ela é verificável quando os corpos diferem. A lição metodológica de 9/out continua valendo
ao lado desta — **dois títulos iguais não provam reincidência, e dois corpos distintos provam**.

A segunda divulgação é mais precisa que a primeira em dois pontos que importam ao livro. Ela nomeia o
`settings.json` como lugar das regras de negação, e dá o exemplo `/etc/passwd`. E acrescenta
**CWE-285, *Improper Authorization***, ao lado do CWE-61: a classificação passa a dizer que o problema é
de autorização e não só de seguimento de link. É a série dos dois leitores reconhecida em taxonomia
padrão — a decisão foi tomada sobre um nome e a leitura ocorreu sobre outro.

Impacto **A** nos caps. 02 e 07.

### 2. ⭐⭐ A mesma primitiva, duas severidades, e os números confirmam

Em 6/out eu notei, por título, que o desvio de negação por symlink era **Baixa** nas duas vezes enquanto a
escapada de sandbox pela mesma primitiva era **Alta**. Os corpos dão os números: **CVSS v4 2,3** nos dois
casos de negação, com impacto de confidencialidade e integridade **baixos**, contra a escapada de
**20/abr/2026** que permite escrita arbitrária fora da área de trabalho e é classificada Alta.

A mesma primitiva de sistema de arquivos, pontuada por consequência: ler um arquivo negado vale 2,3;
escrever fora da área vale Alta. Para o cap. 07 isso é um argumento contra priorizar correção por
severidade quando a **primitiva** é compartilhada — o 2,3 de outubro e o 2,3 de fevereiro são o mesmo
mecanismo que, com outra consequência, dá Alta.

E há um presente de vocabulário. O texto padrão do **CWE-61** diz, verbatim:

> *"The product, when opening a file or directory, does not sufficiently account for when the file is a
> symbolic link that resolves to a target outside of the intended control sphere."*

*Intended control sphere.* Em 3/out o CWE-669 do caso do `gatewayUrl` trazia *"Incorrect Resource Transfer
Between Spheres"*. Duas vezes, em taxonomia padrão, a palavra que o livro usa para fronteira de confiança
é **esfera**. O cap. 07 ganha âncora bibliográfica para um vocabulário que eu vinha usando por conta.

Impacto **B** no cap. 07.

### 3. ⭐⭐ O endereço do opencode, confirmado por mais quatro vias

Ontem eu registrei a troca com base no campo `repository` do `package.json`. Hoje o `README.md` do ramo
`dev` — servido idêntico pelos dois endereços, como é esperado depois de uma renomeação — aponta para
`anomalyco/opencode` em quatro lugares independentes: o selo de status de build, o **tap do Homebrew**
(`anomalyco/tap/opencode`), a referência de flake do Nix e o link da página de releases.

O tap do Homebrew é o que mais pesa, porque é **canal de distribuição** e não hiperlink. Com o manifesto
de ontem, são cinco declarações próprias do projeto apontando para o mesmo dono.

⏳ **Data e motivo seguem ausentes.** Procurei nota de renomeação no README e no manifesto e não achei. O
`package.json` também não traz `bugs` nem `homepage`, que seriam as outras duas vias.

A correção da ficha no Apêndice A é do editor. O que está no meu alcance, e passo a fazer, é usar
`anomalyco/opencode` nas varreduras e registrar o endereço antigo como alias.

Impacto **A** no Apêndice A, como correção de ficha.
