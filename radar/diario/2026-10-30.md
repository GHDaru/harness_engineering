## Achados

### 1. ⭐⭐⭐ O git é uma família de portador, com quatro portas em três harnesses

**gemini-cli v0.66.0**, publicado em **27/out**. A linha, verbatim:

> *"fix(core): disable interactive credential and SSH prompts in getSafeGitEnv"*

Note o nome da função. `getSafeGitEnv` existe para **montar um ambiente de git seguro**, e o que ela não
fazia era desligar os prompts interativos de credencial e de SSH. Ou seja, invocar git podia abrir pedido
de credencial — e, num caminho sem interface, travar.

Isso encosta direto no que eu registrei em 21/out sobre o modo sem cabeça ser onde o mecanismo de
confiança falha, e em 3/out sobre o laço de autenticação com chaveiro sem cabeça. Mas o que ele fecha é
outra coisa, e vale juntar o mês inteiro:

| Porta | Onde apareceu | Harness |
|---|---|---|
| **E-mail do git** — *"arbitrary code execution caused by maliciously configured git email"* | advisory de 9/set/2025, lido em 6/out | Claude Code |
| **Ganchos do git** entre os nove mecanismos de expansão | paper de lavagem de aprovação, 18/out | — (literatura) |
| **Host do git** — *"Closed a marketplace URL validation gap that could allow Git to connect to a different host"* | Codex 0.165.0, 29/out | Codex |
| **Prompts interativos do git** não desligados no ambiente "seguro" | gemini-cli v0.66.0, hoje | gemini-cli |

Quatro portas distintas, três harnesses do corpus, mais a enumeração do paper. O denominador comum é que
**o git é um programa com gramática, configuração e interatividade próprias**, e cada harness o invoca
como se fosse um utilitário mudo. É a mesma estrutura que eu descrevi em 8/out para o `yarn --version` e
em 11/out para o `ripgrep` mexendo na expansão de globs de negação — e o git é o caso mais frequente,
porque todo harness de código o chama.

Para o cap. 07 isso rende uma linha de tabela acima do nível de caso: **git**, com quatro portas
conhecidas. Para o cap. 05, rende o critério: ferramenta externa invocada pelo harness precisa ser
chamada com **ambiente explícito** — sem prompt, sem configuração herdada, sem gramática de endereço
delegada.

Impacto **A** nos caps. 05 e 07.

### 2. ⭐⭐ O classificador de erro casava demais, e isso encosta em três correções do mesmo projeto

Verbatim, mesma release:

> *"fix(core): prevent false positive matches in isAuthenticationError"*

Um predicado chamado `isAuthenticationError` dando **falso positivo**: erro que não era de autenticação
sendo classificado como se fosse.

A adjacência é difícil de ignorar, e eu a registro **como hipótese**. Este mesmo projeto corrigiu laço de
autenticação três vezes em um mês: o chaveiro sem cabeça em 3/out, o *"prevent infinite auth loop from
file contention, headless keyring, and supervisor state drops"* da v0.63.0, e o *"prevent infinite
verification and OAuth retry loops"* da v0.65.0 em 24/out. Um classificador que diz "isto é erro de
autenticação" para erros que não são é exatamente o motor que faz um sistema reautenticar sem parar.

⏳ **A nota não afirma a ligação**, e eu não a afirmo. Registro que as quatro correções vivem na mesma
vizinhança e que a de hoje é a única que mexe no **critério** em vez de no laço.

Estruturalmente, vale notar o espelho. A série dos dois leitores, com trinta casos, é feita de
comparadores que casam **de menos** — a regra não pega o que devia. Aqui um comparador casa **de mais**. O
mesmo defeito de leitura, com o sinal invertido: num caso a política deixa passar, no outro o sistema
reage ao que não aconteceu. Em 24/out eu havia visto o mesmo par com laço composto, barrado por falso
positivo numa semana e usado como portador na outra.

Impacto **B** nos caps. 02 e 07.

### 3. ⭐⭐ Endpoint de rede privada em OAuth de MCP, como escolha explícita

Verbatim:

> *"fix(core): support opt-in private network endpoints for MCP OAuth flows"*

Suporte **opt-in** a endpoints de **rede privada** em fluxos de OAuth de MCP. A leitura que eu sustento: o
caminho existe, e passa a exigir adesão explícita em vez de valer por padrão.

Isto cai no território mais delicado do cap. 07 deste mês. Em 3/out, o CVE do OpenClaw era um
`gatewayUrl` vindo de query string levando token para servidor do atacante. Em 4/out, o corpo do GHSA
mostrava que amarrar o serviço ao loopback não contém o ataque, *"since the victim's browser initiates the
outbound connection"*. Um harness que trata endpoint de rede privada como **escolha declarada**, e não
como caminho disponível, está no lado certo dessa discussão.

⏳ **Não sei o que a adesão protege nem como ela é expressa** — se é configuração gerenciada, variável de
ambiente ou flag. A nota não diz, e a diferença importa, porque adesão que o próprio repositório pode
declarar é adesão que o atacante declara.

Impacto **B** no cap. 07.
